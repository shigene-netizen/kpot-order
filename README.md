## 二、客人点餐流程

1. **扫码** → 打开点餐页（桌卡上的码会自带桌号，自动切到「堂食」）
2. **选类型** → **默认堂食**（填桌号）/ 自取 / 外送
3. **点餐**
   - **Hot Pot To Go**：6 步自选锅 $15.99 —— 汤底 → 面 → 蛋白 → 配料 → 3 样蔬菜 → 蘸酱，可加 $3.99 套餐（汽水 + 2 个春卷）
   - **BBQ To Go**：1 荤 $12.99 / 2 荤 $15.99 / 3 荤 $18.99，每碗附白饭 + 泡菜 + 烤蔬菜；同一款蛋白可以重复选
   - **Drinks**：汽水 $2.99 / 奶茶 $4.99 / 果茶 $4.99 / 特调柠檬水 $4.50
   - **A La Carte**：12 款小食 $1.50 – $12.99
4. **购物车** → 改数量、选小费（0 / 15% / 18% / 20% / 25%）
5. **结账** → 填姓名、手机号、取餐时间，选付款方式
6. **下单** → 生成订单号（如 `KP-261002-001`）+ 二维码票据，客人出示给柜台

## 三、付款方式

`assets/config.js` 里的 `CONFIG.payment` 控制。默认开启「到店付款」，其余按需打开：

| 方式 | 说明 | 需要准备 |
|---|---|---|
| `counter` | 到店付现金 / 刷卡（默认开启，**大单除外，见下**） | 无 |
| `stripe` | 线上刷卡、Apple Pay、Google Pay（**已开启，默认选中**） | Stripe 账号 + 密钥 |
| `venmo` | 跳转 Venmo 转账 | Venmo 商家账号 |
| `zelle` | 展示 Zelle 收款信息，客人手动转账 | Zelle 邮箱 / 手机号 |

> 只要 Stripe 没配好，客人端就**只会看到「到店付款」**——不会出现点了没反应的按钮。

### 到店付款的金额上限（防止跑单）

**问题**：到店付款的订单会**先到厨房、后收钱**。客人下单后不来取，食材成本就是纯亏损，
而且**单越大越疼**。

**做法**：`CONFIG.payment.counter.maxTotal`（当前 **$30**）以上的订单**必须线上预付**。

| 订单金额 | 到店付款 |
|---|---|
| ≤ $30 | 可以选（保留现金客人的便利） |
| > $30 | 不可选，客人看到置灰的卡片 + 原因，自动切到 Pay Online |

三层保护，缺一不可：

1. **默认选中 Pay Online** —— 客人没主动改的话，订单在厨房看到之前就已经付过款了。
2. **客人端置灰** —— 超过上限时「Pay at Counter」变灰并写明原因，不会走到死路。
3. **服务端强制拦截** —— 真正的防线在 `server.js` 的 `counterCapVerdict()`。
   前端置灰只是提示，**规则必须在收单的地方再查一遍**，否则改一下前端就能绕过。

两个刻意的设计：

- **超限时 fail closed** —— 直接拒单（返回 `counter_over_cap`），不是放行。
- **没有线上支付方式时不启用上限** —— 否则配错了会把所有大单堵死，
  比它要防的风险更糟。所以 `maxTotal` 只在 Stripe 真的可用时才生效。

改上限：编辑 `assets/config.js` 的 `maxTotal`。填 `0` 或删掉这一行 = 关闭上限。

> ⚠️ 客人端拿到的 `total` 必须和服务端重算的一致，上限比对的是**服务端重算后的金额**
> （含税、含小费），不是浏览器报上来的数字。

## 三点五、给客人打折（优惠码 + 店员打折）

店主后台（`/kpot/staff/console/`）新增一张 **🏷️ Discount Codes** 卡片，
客人点餐页购物车新增一个 **Discount Code** 输入框。两种用法：

| 用法 | 谁触发 | 适合 |
|---|---|---|
| **优惠码** | 客人自己输（海报 / 外卖单 / 群发） | 促销活动 |
| **店员打折** | 店员在看板上对某一单打折 | 补偿某位客人、熟客、投诉 |

店主要在后台卡片里建码：**码名 / 类型 / 数值**，另外三项都可选：
**最低消费**、**最多可用次数**、**过期日期**。建好后随时可以
**Enable / Disable / Delete**。

### 三种折扣形式

| `type` | `value` 填 | 效果 |
|---|---|---|
| `percent` | `10` | 小计减 10% |
| `amount` | `5` | 小计减 $5 |
| `freeship` | 忽略 | 减掉配送费（小计不动） |

### 四条必须知道的规则（都是服务端定的）

1. **税按折后价算。** 商家折扣的通行做法：客人为实际付的钱交税，
   不是为划掉的原价交税。
2. **折扣不能超过可减的东西。** 满 50 减 50 的码用在一张 $20 的单上，
   减 20，**不会**变成负数；免配送费的码用在自取单上，减 0。
3. **一单一折。** 店员打折会**替换**掉这单已有的优惠码，不叠加。
   两笔折扣悄悄加起来，比任何一种单独折扣都危险。
4. **码只在订单真正落成时消耗。** 客人打开 Stripe 收银台又关掉，
   **不会**用掉一个码。只有「订单创建成功」才算。

### 两种角色，两套把关

- **店员打折**：手工输入的数字**超出订单金额时直接报错**，不像客人码那样
  默默截断。`999` 打在一张 $16.95 的单上，是应该报错而不是把菜免掉。
- **优惠码**：在 `pricing.js` 里截断，因为那是**店主配置错了**，
  不该让客人付更多。

### 店主怎么操作

**建码（后台默认页）**：`🏷️ Discount Codes` → 填码名 / 选类型 / 填数值 →
`Add code`。管理码需要 **admin key**（和看板同一把，浏览器内只需输一次）。

**给某单打折（厨房看板）**：订单卡片上多一个 **🏷️ Discount** 按钮 →
选类型、填金额 → `Apply`；`Remove` 撤回。

> 看板 4 秒刷新一次，所以折扣输入用的是**弹窗**而不是卡片内联表单——
> 内联表单会在人还在打字时被刷新抹掉。

### 技术实现（为什么长这样）

**折扣一律在服务端算**，前端只是输入框，和价格一个道理。
`/api/price` 是给客人看一眼的预价接口（不建单、不消耗码），
下单时 `/api/checkout` 和 `/api/orders` 各自再解析一次。

**Stripe 收负数行项目是行不通的**（实测：

```
"Invalid non-negative integer"  param: line_items[1][price_data][unit_amount]
```

）。所以折扣走 **Stripe coupon**：服务端把已经算好的金额铸成一个
一次性 coupon 挂到 session 上，`amount_total` 精确等于我们算的 `total`
（因为税行按折后价算，减去 coupon 正好抵消）。coupon 创建**失败时直接
拒绝下单**，绝不回退到收全价——那比报错糟得多。

优惠码存在 `discounts.local.json`（重启 / 重发布都不丢），
测试用 `KPOT_DISCOUNTS_FILE` 指到临时文件。

### 开启线上刷卡 —— 两条路，选一条

**两条路都完全不需要在 Stripe 建 Product。**

#### ▶ 路线 A（推荐）：用项目自带的小后端，金额自动带入

客人**一个字都不用输**，结账页直接把准确金额带进 Stripe。

1. 到 **stripe.com** 注册 / 登录
2. 后台 → **Developers → API keys** → 复制 **Secret key**（`sk_live_...` 或测试用的 `sk_test_...`）
3. 在项目目录里复制密钥文件模板：

   ```bash
   cp secrets.local.json.example secrets.local.json
   ```

4. 打开 `secrets.local.json`，把密钥填进去：

   ```json
   { "stripeSecretKey": "sk_live_xxxxxxxxxxxxxxxx" }
   ```

   （或者用环境变量 `STRIPE_SECRET_KEY`，两种都认）

5. 用 `npm start`（而不是静态文件服务器）启动

页面会通过 `/api/health` 自动发现后端，并把支付方式切成「金额自动带入」。
`config.js` 里**什么都不用填**。

#### ▶ 路线 B：纯静态托管（没有后端）

如果只想把文件丢到任意静态空间，就用 Stripe 自带的 Payment Link：

1. 后台 → **Payment Links** → **+ New**
2. 在「Select a product or service」这一步，**直接选「Customers choose what to pay」**
   —— 不要去点「+ Add a product」
3. 填标题（如 `KPOT To Go`），币种 **USD**，设最小 $1 / 最大 $500
4. **Create link** → 复制链接（形如 `https://buy.stripe.com/abc123XYZ`）
5. 填进 `config.js`：

   ```js
   stripe: { enabled: true, paymentLink: 'https://buy.stripe.com/xxxxxxxx' }
   ```

**客人怎么付**：结账页会把准确金额用大字显示，旁边有 **Copy** 按钮。
客人复制金额 → 点 Place Order 跳到 Stripe → 粘贴 → 付款，不会输错。

> 两条路可以同时留着：有后端时优先走后端（自动带入），
> 后端不可用时自动降级到 Payment Link。

## 四点五、手动开关：临时关掉某一种下单方式

后台 **Live Orders（厨房看板）** 页面顶部有两组开关：

**Store status（整店）**

| 开关 | 作用 |
|---|---|
| Accepting orders | 暂停接单。客人还能浏览菜单，但下不了单 |
| Store open | 整店打烊。客人看到「🔒 currently closed」 |

**Order channels（按方式）**

| 开关 | 关掉后 |
|---|---|
| 🍽️ Dine-In | 堂食点单不可选 |
| 🛍️ Pickup / To Go | 自取不可选 |
| 🛵 Delivery | 外卖不可选 |

典型场景：**外送司机今天没上班 → 只关掉 Delivery**，自取和堂食照常，
不用整店停业。

### 客人那边会看到什么

**默认落在 Dine-In**（2026-10-07 由店主定）。这里有个容易踩的地方：
「默认渠道」由**两处**共同决定，必须一致——

- `assets/config.js` 的 `orderTypes[]`：**数组顺序就是显示顺序**，
  第一项还是 `resolveOrderType()` 找不到客人已选项时的兜底；
- `assets/app.js` 的 `state.orderType`：开局选中项。

所以两处都写了 `dinein`。**只要有一处没改**，就会出现「带桌号的码进来是堂食、
普通链接进来是自取」这种半截状态。`probe_guest_defaults` 就是钉这个的：
它同时断言**第一张卡是 Dine-In**、**默认选中 Dine-In**、
以及**把 Dine-In 关掉后回退到 Pickup（第一张还开着的卡）而不是留在死卡上**。

关掉的渠道**不会消失**，而是变灰、划线，副标题写成
「Not available right now」—— 直接藏掉会让客人以为网站坏了。
如果客人正选着这个渠道，会自动切到还开着的那个，并弹提示。
三个全关时，顶部出现横幅「我们不接线上单了，请电话或到店」。

> 用假时钟测过：周日 8:00 PM 显示「Open now · closes 9:30 PM」（新营业时间内）。

### 服务端会兜底

**关键**：客人手机上藏起来只是提示，真正的拦截在服务端。
`POST /api/checkout` 会再用同一套规则检查一遍，被关掉的渠道直接返回：

```json
{ "error": "type_off", "message": "We are not taking delivery orders right now." }
```

也就是说，就算有人改了浏览器里的代码硬发请求，也刷不过去。

### 开关存在哪（重要）

保存在 **`store.local.json`**（已被 `.gitignore` 屏蔽，网上也读不到，
返回 404）。

> ✅ **已修复的老问题**：这些开关以前只存在内存里，**每次重新发布都会
> 悄悄重置成「全开」**——店主把 Delivery 关了，下次一发布它自己又回来了。
> 现在落盘保存，重启 / 重新发布都还在（已实测：重启后状态保持）。

修改后立刻生效，**不需要重新发布**，也不用重启。

**Kitchen automation（第三组，同一个页面）**

| 开关 | 作用 |
|---|---|
| 🚀 Auto-start cooking | 客人下单后不用员工点 PREPARING，订单自己进厨房并自动出票 |

规则（服务端定，客人改不了）：

| 渠道 | 什么时候自动 |
|---|---|
| 🍽️ 堂食 | **一到后台就自动**——人就坐在店里，跑单风险极小 |
| 🛍️ 自取 / 🛵 外卖 | **等付款确认**：客人的手机从 Stripe 回来，或员工点了 💳 Re-check payment |

两道必须理解的门：

- **开关默认是关的**，只能由店主在后台打开。重新发布不会悄悄开始替无人把关的单子做饭。
- **客人自己声称「已付款」不算数**。下单接口是公开的，`{"orderStatus":"verified"}` 谁都能 POST；
  那个值会照存、照显示（这正是 Re-check 要纠的错），但它不能启动烤炉。
  只有 Stripe 的回答、或带 admin key 的 PATCH 算确认。

其余行为与手动点 PREPARING 完全一致：同一张票据、同一个按订单号幂等的队列，
所以重复触发不会出两张票，卡纸了照样有 Reprint。员工随时可以手动点，
`received` 之外的状态一律不动（已取消的单不会被复活）。

> 这条规则的服务端实现在 `server.js` 的 `shouldAutoPrepare()` /
> `maybeAutoPrepare()`（`storeGate` 附近），三个触发点：
> 下单时、`settleBoardFromStripe()`（覆盖 Stripe 回跳和 Re-check 两条路）、
> 以及 PATCH 里员工手改 paymentStatus。测试 `_dev/test_auto_prepare.js`。

## 四点六、外送只送 2 英里：超距自动拦截，引导改自取

**规则（2026-10-18 店主定）**：外送只送店铺周围 **2 英里**。超出的一律
**不让下单**，请客人改选自取或堂食。菜单卡片和官网落地页都已从 5 英里
改成 2 英里。

### 怎么量距离

`geo.js`（零依赖）按三级走，**只有拿到实在证据才拦**：

| 级别 | 做法 | 结果 |
|---|---|---|
| 1. 街道级（可信） | 用**美国人口普查局免费地理编码**（无需密钥）把地址变成坐标，和店铺坐标算 Haversine 直线距离 | ≤2 英里放行，>2 英里 **拦截** |
| 2. ZIP 码兜底 | 地址编码不出来（新小区、写法生僻）时，查内置的附近 ZIP 质心表；质心在 2+1 英里内放行，超出 **拦截** | 精度换覆盖，只在兜底时用 |
| 3. 量不了（**故障开放**） | 地理编码服务挂了、地址无法定位 | **放行**，订单照收——地址照印在厨房小票上 |

> 第 3 条是故意的：**不能因为政府网站打不开就让店开不了张**。
> 拦截只发生在「有实据超距」时。

### 在哪拦截（两道，都是服务端）

1. **`POST /api/checkout`**（创建 Stripe 会话前）——钱还没移动就被拦下
2. **`POST /api/orders`**（订单上看板前）——按**生效渠道**判断，改包名绕不过

两道都返回：

```json
{ "error": "delivery_out_of_range", "miles": 9.2, "radius": 2,
  "message": "That address is about 9.2 miles from us — we deliver within 2 miles. Please choose Pickup or Dine-In." }
```

### 客人那边（提前告知，不用等付钱）

结账页选 Delivery 后，地址框边打边查（`POST /api/delivery/check`）：

- **超距**：红卡片说明原因 + 「Switch to Pickup」一键转自取，**Place Order 同时变灰**
- **在范围内**：一行小绿字（街道级还会写上「离我们 0.7 mi」）
- **查不到**：一行小灰字说明情况，**照样能下单**（和服务端故障开放一致）

自取 / 堂食的单完全不查——那个框填的是取餐时间或桌号。

- `_dev/probe_delivery_geo_http.js`（29 项，起真服务 + 假 Stripe，两道拦截都验）

## 四点七、打烊后不接单：下单接口也认营业时间

`POST /api/checkout`（收钱那一步）从第一版起就用 `storeGate` 拦打烊后的单，
但 `POST /api/orders`（真正把订单写上看板的那一步）**从来没拦过**。客人页面把
每一条路都堵了（加购、开购物车、开收银台、换渠道都查 `ordersBlocked()`），
诚实客人走不到那里；直接手搓一个 POST 可以：**店都关了，订单照样落在看板上**，
店主的手机还会收到新订单邮件 + 推送。2026-10-18 用
`_dev/probe_closed_orders_http.js` 证实了这件事（补丁之前它是红的）。

### 店主定的规矩：只拦「还没付钱」的单

| 情况 | 打烊后 |
|---|---|
| 到店付款（`payMethod: 'counter'`） | **409 `closed`** —— 这单写上看板时还没人付钱，拒了客人毫无损失，厨房也毫无损失 |
| 在线支付中（`payMethod: 'stripe'`） | **照常接收** —— 客人页面在 Stripe 交出会话的那一刻就写下这单，**钱还没到**；21:29 付过款的客人 21:31 回来，不能发现自己的单没了。厨房可以拒看板上的单，没法变出一条从没写上去的单 |

（已知残留：手搓一个声称在线支付的单还是会落上看板，只是带着「未付款」的标记——
跟诚实的客人正在付款中的状态一模一样，要区分得跟 Stripe 问一句，看板上本来就
显示它未付。）

「打烊」的判定和收银台、客人页面完全一致：**店主的手动开关 + 营业时段**都要
通；已经定好次日的时段配送单是关于明天的，不被今晚的时钟挡。

### 这一改动的测试代价

`/api/orders` 开始认时钟之后，**所有会 POST 到店付款单的测试套件**在晚上跑就会
被拒（真实时段 12:00–21:30，测试大多在半夜跑）。它们统一钉上
**`KPOT_HOURS_SPEC='{"openMinute":0,"closeSunThu":1440,"closeFriSat":1440}'`**
（全天营业）——营业时间 tick 每 `FLUSH_MS` 就用时钟刷新 `open`，所以**光用
`/api/store` 把店打开是不够的**，一个 flush 之后就被改回去（这就是
`probe_delivery_geo_http` 时红时绿的原因）。生产环境不设这个变量。

## 四点八、司机端：今天的外送按顺序送

店主要一个「后台把外送单按时间和地址排好给司机」的队列。2026-10-18 店主拍板：
**独立司机页面**、**独立司机钥匙**、**先按时间窗、同窗内近的优先**。

打开 **`https://order.kpotexpress.com/driver.html`**（手机优先，可「添加到主屏幕」，
像看板一样全屏打开）。输一次司机钥匙，**从上到下就是送货顺序**。

### 排的是哪些单

| 进队列 | 不进队列 |
|---|---|
| 今天的配送单（未完成、未取消） | 明天及以后的预订（还没到那天） |
| 前几天送不掉、还开着的单（卡上标 **LEFT OVER**） | 已完成 / 已取消 |
| 未付款的单（卡上大红 **NOT PAID**，司机照送，收钱的事柜台处理） | 自取 / 堂食 |

### 排序规则（dispatch.js，纯函数）

1. **配送时间窗** —— 早的窗先送，永远。12 点的三单永远排在 2 点那单前面。
2. **同一个窗内按距离**，近的优先。距离用**下单时就算好的坐标**（2 英里闸门那次
   地理编码，直接存在订单的 `geo` 字段上，不重复花钱）；老订单没有坐标就退回
   ZIP 质心；两者都没有 → **排在这个窗的最后**，绝不插到最前面。
3. 还分不出先后 → 按下单时间，再按单号。**排序是全序**，所以司机刷新页面不会
   看到队伍悄悄重排。

每张卡上：序号（大字）、时间窗、距离（`0.7 mi`；ZIP 估的会写 `(ZIP)`）、**地址
（点一下直接跳 Google Maps 导航）**、客人姓名 + 可点的电话、袋子里有什么
（按厨房自己的行，不是客人嘴里的）、客人备注、总价、付没付。

### 司机只能做一件事

司机钥匙（`DRIVER_KEY`）只允许 **`GET /api/driver/queue`** 和 **把一单配送单标记
成「已送达」**。改时间、改价、改支付状态、动自取单、动已取消的单——全部拒绝
（`driver_readonly` / `driver_not_delivery` / `order_cancelled`）。店主自己的
admin key 照样什么都能做（也能开这个页面看自己的队），反过来不行。

> **第三把钥匙，和另两把互不相通**：`ADMIN_KEY`（看板）、`PRINT_KEY`（打印代理）、
> `DRIVER_KEY`（司机）。它**故意 fail closed**：没设 `driverKey` 时队列接口返回
> 401——不像打印接口在「什么都没配」的开发模式下会敞开，因为这个接口吐出的是
> 客人住在哪、电话多少。
>
> 生成一把（和另两把**不同的值**）：
> ```bash
> node -e "console.log(require('crypto').randomBytes(18).toString('base64url'))"
> ```
> 写进 `secrets.local.json` 的 `"driverKey"`，或设环境变量 `DRIVER_KEY`（环境变量优先）。
> 钥匙只存在**司机自己那台手机**上，页面底下有 **Forget this phone** 一键抹掉。

### 测试

- `_dev/test_dispatch.js`（纯逻辑：进不进队列、窗口优先、同窗就近、异常单垫底、排序稳定）
- `_dev/probe_driver_http.js`（钥匙矩阵：没钥匙/错钥匙/打印钥匙 401，司机钥匙和店主钥匙 200；
  司机只能「送达」；没配 `driverKey` 的服务是锁着的；2 英里闸门测出的坐标确实存进了订单）
- `_dev/probe_driver_ui.js`（真浏览器：钥匙门、顺序、卡片内容、点 Delivered 后卡片消失并重排队号、
  送完显示空状态、Forget this phone 重新上锁）

## 四点九、外送满 $10 才送：一道新的钱关口

2026-10-19 店主要求：**外送单设定最低消费 $10 才可以外送**。2 英里规则（四点六）
决定**送到哪**，这一条决定**多大的单才配上一趟车**——为一份 $6 的 Bowl 跑一趟街

- 只卡**外送**。自取、堂食多小的单都行——同一辆车的成本只在外送上发生。
- 按**折前的食品小计**（小票上印 `Subtotal` 的那行）算：优惠码、积分兑换、税、
  小费、配送费都不参与判断。客人在小票上能看到的数字，就是被拿来评判的数字，
  拒绝时才不像讹人。
- **无论怎么付款都卡**。外送本来就是预付的（到店付款在外送上直接被禁，见三点五
  附近），所以不像 $30 上限那样需要「没有线上支付就放行」的豁免——这条关的是
  **这趟车**，不是**风险**。
- 数值在 `assets/config.js` 的 `delivery.minSubtotal`（当前 `10`，`0` = 不设限）。

### 在哪拦截（两道，和服务端其它规矩一样）

| 关口 | 时机 | 结果 |
|---|---|---|
| `POST /api/checkout` | 2 英里闸之后、进 Stripe 之前 | 409 `delivery_below_minimum`，**Card 根本不会被刷** |
| `POST /api/orders` | 2 英里闸之后、付款方式规则之前 | 409 `delivery_below_minimum`，**订单不会落到看板** |

放在距离闸之后：一个又小又远的单，先报地址的问题（换地址比加菜更基本）。放在
付款方式规则之前：一份 $6 的外送先被说「太小」，不会先被说「不能到店付」——
客人要修的是购物车，不是付款方式。

### 客人那边

购物车小票的配送行下面多一行金色提示：**`Delivery minimum $10.00 — add $2.02
more`**，加着加着就消失了。客人页的提示和服务器判的是同一个数（折前小计），
一个 $12 的购物车兑掉 $3 积分照样过 $10 的线。客人硬要点下去，两道关口会把
同一句话原样弹回来。

## 四点十一、储值码：一个「余额」，不是一张一次性券

LUCKY 66 的奖品官方规则承诺了三件事：**每笔单自动扣余额、不够时别的方式补上、
付完显示还剩多少**。在 2026-10-22 之前，这三件事一件都不存在——那个 `$66` 只是
中奖邮件里的一句话，订单系统里没有任何一条代码路径认得它。

### 一句话

`credits.js` 是一本账：**一个码 = 一份可以分开花的余额**。`appliedFor =
min(balance, subtotal)`，所以 `$66` 的码付 `$31.98` 的吃的，这单扣 `$31.98`，
码里**还剩 `$34.02`** 下次接着用。

### 为什么不是「一次性券」

优惠码（`discounts.js`）和储值码看起来像，其实是两种东西，混在一起就会算错钱：

| | 优惠码 | 储值码 |
|---|---|---|
| 能付多少 | 面额一次用完 | 可以只付一部分 |
| 用完 | 消失 | 余额变少，码还在 |
| 客人要知道 | 省了多少 | **还剩多少** |

### 五条规矩（全是服务端定的，前端改不动）

1. **金额永远服务端重算。** 三个计价点（`/api/price`、`/api/checkout`、
   `POST /api/orders`）都自己问一遍账本，浏览器说「我用了 $31.98」不算数。
2. **一单只能用一种折扣。** 储值 + 优惠码 + 积分/券，三选一，服务端
   `one_discount_only` 409；前端每个 setter 也会把另外两种清掉。
3. **整数 $0 的单不走 Stripe。** 全额覆盖的订单总计 `$0.00`，而 Stripe
   **拒绝空的行项目列表**——所以 `handleCheckout` 直接返回
   `{url:null, covered:true}`，一次都不调 Stripe。客户端随后用
   `payMethod:'credit'` 落单，服务端**用自己的 $0 算术**推导出
   `paymentStatus:'verified'`，不是听浏览器说「我付了」。
4. **部分覆盖照常刷卡。** 差额走 Stripe，一分不少。
5. **取消只退一次。** `order.credit.released` 守着，退过的不能再退，
   而且最多退回原来花掉的数。

### 积分安全（这条最容易被绕）

`pointsBaseFor = subtotal + delivery − discountAmount`——**折扣要从积分基数里
减掉**。否则一个全额覆盖的订单食品小计 `$31.98`，等于白送 31.98 分，
奖励机制可以被免费食物刷爆。盖章仍然算（店主定的「一单一章」不变）。

### 三处界面

- **客人页**：结算页多一个 Store Credit 框（`features.storeCredit` 管显示，
  服务端管执行），输码即显示「这单扣多少、码里还剩多少」——规则承诺付完才告诉
  客人，没有理由让他等到出票。
- **厨房票 / 看板**：票上多一行 `CREDIT LEFT`，看板上 `💳 $X credit left` 小 pill。
- **后台 `🎁 LUCKY 66`**：发奖时**留空就自动生成一个强码**，且开出来立刻就能花；
  兑换行可以查任意码的余额。

## 五、把订单送到厨房

默认情况下，客人手机上会显示订单票据，出示给柜台即可，**不需要任何服务器**。

想自动推送订单，在 `config.js` 里填 webhook：

```js
dispatch: {
  webhookUrl: 'https://hooks.zapier.com/hooks/catch/.../'
}
```

支持 Zapier / Make / n8n / Google Apps Script / 自建 API —— 下单时会把完整订单以 JSON POST 过去。

```json
{
  "no": "KP-261002-001",
  "orderType": "pickup",
  "customer": { "name": "Alex Chen", "phone": "(555) 123-4567" },
  "items": [
    {
      "name": "Build Your Own Hot Pot", "qty": 1, "unit": 19.98,
      "mods": ["Miso Broth", "Ramen", "Thinly Sliced Beef"],
      "addons": ["Make It a Combo (+$3.99)"]
    }
  ],
  "subtotal": 25.97, "tax": 1.56, "tip": 4.67, "total": 32.20,
  "payMethod": "counter"
}
```

### 看板上的付款标记（交付前必看）

厨房看板每张订单卡上有一个**付款标记**，交付前请务必确认：

| 标记 | 含义 | 该做什么 |
|---|---|---|
| 🔴 `UNPAID · collect $16.95` | 到店付款，**还没收到钱** | 收钱后再把餐交出去 |
| 🟢 `PAID` | 线上已付款（服务端已向 Stripe 核对） | 直接交付 |
| 🟡 `NOT CONFIRMED · $16.95` | 线上付款**没核对成功** | 先点 **💳 Re-check payment**（见下），再决定 |

> 红色 `UNPAID` 是**故意做成整张卡上最显眼**的东西——那是我们还没收到的钱。
> 早期版本只把原始状态词（`counter`）用小字显示，样式和普通订单一样，
> 结果就是**容易看漏、把没付钱的餐交出去**。

#### 黄色 `NOT CONFIRMED` 时：点「💳 Re-check payment」

线上刷卡的订单，看板是**靠客人的浏览器回来报信**才知道钱收到了。
如果客人**付完钱直接关掉页面**（或者手机没电、切走了 App），这条报信就永远
不会发生——**钱已经收了，看板却一直停在没核对的状态**。

2026-10-07 真事：`KP-261007-001`（$13.77，Stripe 上 `payment_status: paid`）
在线上看板显示为 `PENDING`，因为那一单**从来没有被结算过**。
钱没丢，丢的是**看板上的信息**——而员工分不清「已付款但没报信」和
「根本没人付钱」，就只能重复收钱或者不敢交餐。

所以线上刷卡、又还没确认的订单卡上会多一个 **💳 Re-check payment** 按钮：

- 点它 → **服务端**拿订单号去 Stripe 查（订单号存在 `client_reference_id` 里），
  用 **Stripe 自己的答复**结算看板。客人说什么、请求里写什么都不算数。
- 查到已付 → 变绿 `PAID`；查到未付 → 订单按放弃处理；查不到 → **什么都不动**。
- 按多少次都安全（Stripe 是唯一事实来源，答案不会变）。
- 到店付款的订单**没有**这个按钮（它压根没有 Stripe 会话）；
  已确认的订单也没有（没什么可查的了）。

> ⚠️ **查不到会话 ≠ 客人没付钱。** 也可能是查询本身没找到（时间窗不对、
> Stripe 抽风）。所以「查不到」**绝不取消订单**——必须留给人工判断。
> 这一条有测试专门盯着（`_dev/test_recheck_payment.js` 里
> "an order with no Stripe session is NOT cancelled"），故意改坏会红 3 个断言。

**时间窗是「不对称」的（订单前 6h / 订单后 26h），别改成对称的。**
订单是**先记到看板、再交给 Stripe**的，所以会话**永远在订单之后**创建——
订单之前没什么可找的。真正需要留余量的是**之后**：一个 Checkout 会话
有效期 24h，客人走开再回来重试会**新建一个会话**。窗口如果只开到订单后 6h，
那次重试就落在窗外，我们会找到**旧的、未付的那个会话**，然后告诉看板
「没付款」——**正好是这个功能要防的错误答案**。
（有测试钉住：`a session created 8h after the order is still found`，
把窗口改回 6h 会红 2 项。）

## 五点五、自动打印厨房单（收据打印机）

员工在看板上点 **PREPARING**，厨房打印机就吐出一张厨房单。
不需要人盯着屏幕抄单子。

```
[手机/平板: 点 PREPARING]  →  PATCH /api/orders/:id
        ↓
[云端 server.js]  把「厨房单」排进打印队列（落盘，重启不丢）
        ↓
[店里常开的 Windows 电脑]  每 2 秒来取一次（print-agent）
        ↓
[网口/WiFi 热敏打印机]  TCP 9100  → 吐出厨房单
```

**完整安装步骤见 [`print-agent/PRINT-AGENT-SETUP.md`](print-agent/PRINT-AGENT-SETUP.md)。**
（装 Node.js → 填打印机 IP → 双击 `start.bat` → 设开机自启）

### 网站地址会变，但不用去店里改文件

店里那台电脑**不需要知道网站的地址**，它是**查来的**：

```
[GitHub Pages 转发页]  ← 永远不变的地址（二维码就印它），上面写着当前网站地址
        ↓  每 5 分钟读一次；连不上或收到 400 就立刻再读
[店里那台电脑]
```

所以**发布完不用跑一趟店里**。以前不是这样：地址写在
`print-agent/config.json` 里，每次发布都要手动改，**忘了改打印就静默停摆**
（看板只显示「代理很久没连上」，看不出是地址变了）。

三个刻意的设计（`_dev/test_agent_discovery.js` 钉住，25 项）：

1. **剥注释再匹配 `baseUrl`。** 「注释掉旧地址、把新的粘在下面」是最自然的改法，
   直接匹配第一个会**悄悄跟着旧地址跑**。
2. **查不到地址绝不清空正在用的地址。** 转发页抽风不是停止打印的理由。
3. **收到 400 立刻重查**，不等下一个周期（重新发布后旧地址正是这个反应）。

> 想固定死地址：把 `discoveryUrl` 填 `""`，再填 `serverUrl`。

### 看板上的打印标记

| 标记 | 含义 | 该做什么 |
|---|---|---|
| 🖨️ `QUEUED` | 已排队，等店里电脑来取 | 等一下 |
| 🖨️ `PRINTING…` | 正在打 | 等一下 |
| 🖨️ `PRINTED` | 打好了 | 无 |
| 🖨️ `REPRINTED` | 这是补打的 | 无 |
| 🖨️ `PRINT FAILED` | **没打出来** | 检查打印机，点 **Reprint** |

订单列表上方还有一行**打印机健康状态**，它刻意区分三种「看起来一样」的故障，
因为修法完全不同：

| 显示 | 真正的问题 |
|---|---|
| 🔴 `No print agent has ever connected` | 店里那台电脑上的程序**没在跑** |
| 🔴 `Print agent last checked in N min ago` | 电脑睡了 / 断网 / 窗口被关了 |
| 🔴 `N ticket(s) failed to print — <原因>` | 电脑在跑，但**打印机没吃下纸**。原因写在红条里，末尾是它试的地址（`— tried 192.168.1.50:9100`） |
| 🟡 `N ticket(s) waiting to print…` | 排队中（一直不动就是上面某一种） |
| 🟢 `Printer ready` | 一切正常 |

#### 打印失败时，报错必须写明它试的地址（2026-10-13）

起因是店里真实发生的一次故障：打印机换了 IP，出纸全失败，而看板只写
`3 ticket(s) failed to print` —— **知道失败了，但不知道该去哪查**。

现在两处都改了：

- **打印代理**：每一条失败信息都带上它实际拨的地址，例如
  `timed out after 0/965 bytes — tried 192.168.1.50:9100`。
  这个后缀是**统一追加**的（`printBytes()` 里的 `fail()`），不是每个分支各写一遍，
  所以以后新增的失败路径也不会漏。
- **看板红条**：把最后一条失败的原因原样显示出来，不再只报个数。

⚠️ 注意区分两种失败，它们的**修法不同但报错很像**：

| 报错 | 含义 |
|---|---|
| `printer refused the connection (is it switched on?)` | 对方**明确拒绝**了（ECONNREFUSED）—— 通常是对面没开、或者端口不对 |
| `timed out after 0/965 bytes` | 连接**根本没建立**（一个字节都没出去）—— 通常是 **IP 变了 / 不在同一网段 / 被防火墙丢包** |

两种都**不是**「打出来了」，所以都不会被误记成成功。

> 另外：服务器要重试 `PRINT_MAX_ATTEMPTS`（默认 10）次才把票标记为 `failed`，
> 退避是 2s、4s、8s…最多 60s，所以**红条大约 5 分钟后才出现**。
> 测试用 `KPOT_PRINT_MAX_ATTEMPTS=1` 这个测试缝把这个过程压到 1 次，
> 否则一个套件要跑五分钟。生产环境不要设它。

### 纸宽 / 切纸 / 总开关

在 `assets/config.js` 里：

```js
printer: {
  enabled: true,   // false = 完全停止排单，看板不再显示打印状态
  paper: '80',     // '80' = 80mm（48 字符）  '58' = 58mm（32 字符）
  cut: true        // 没有切刀的老机器改成 false
}
```

打印机的**地址不在这里**，它在店里那台电脑的 `print-agent/config.json` 里——
这个文件跑在云端，够不着你店里的局域网。

### 两个必须理解的设计取舍

**1. `PRINTED` = 「字节全部发出」，不是「机器确认纸出来了」。**
裸 TCP 9100 的打印机收下数据就关连接，**没有「打印成功」的回执**。所以：
写完 = 成功，写到一半断 = 失败。把「没收到确认」当失败会导致**重发**，
厨房拿到两张一样的单子——比偶尔漏报更难处理。纸用完了它**看不出来**，
所以看板上必须保留 **Reprint** 按钮。

**2. 排队是「租借」式的。** 电脑取单 → 租借 2 分钟 → 打完回报。
电脑中途崩了，租借到期，单子**自动回队列**。一台电脑崩掉不会吞掉订单。

### 为什么票据在服务端生成

`printer.js` 只做「把订单变成字节」。店里那台电脑**只搬字节**，
不知道票据长什么样。所以改票据版式**永远不用碰店里那台机器**——
那是整套系统里最难远程维护的东西，让它尽量少变。

票据版式是「一份版式、两个后端」：`buildTicket()` 产出样式指令，
再分别渲染成 **ESC/POS 字节**（给打印机）或**纯文本**（给后台预览）。
所以后台看到的预览和真打出来的**不可能走样**。

### 不用打印机也能测

```bash
node _dev/test_printer.js          # 票据版式，逐字节（73 项，无需硬件）
node _dev/probe_print_flow.js      # 真服务端 + 真代理 + 假打印机（24 项）
node _dev/probe_board_print_ui.js  # 真浏览器里看标记、点 Reprint / Re-check（29 项）
node _dev/probe_guest_defaults.js  # 真浏览器里客人默认落在哪个渠道（14 项）
```

`_dev/fake_printer.js` 是个假打印机（TCP 服务），所以整条链路**不用买机器就能测**。

## 五点八、会员积分 + 回头券（⚠️ 2026-10-14 写完、测完，**尚未发布**）

> **状态：本地完成，一行都没上线。** 24 个套件全绿，但这个功能客人还看不见。
> 发布它之前不要改 `customers.js` 的规则——积分和券都是**钱**，规则一改，
> 已经在跑的会员表就对不上账。

### 一句话

客人留个手机号就能成为会员。**吃的每一块钱攒 1 分**，200 分抵 $5；
每满 10 单送一张 $10 券；另外每笔已付款的订单都会**发一张 $5 回头券，
14 天有效**——目的是让上个月来过的人这个月再来。

### 五条规则（都是服务端定的，前端改不动）

| 项 | 值 |
|---|---|
| 积分 | 吃 **$1 = 1 分**；**200 分抵 $5**，可按 200 的整数倍抵 |
| 盖章 | 每满 **10 单** 送一张 **$10** 券（不限期） |
| 回头券 | 每笔**已确认付款**的订单一张 **$5，14 天**有效 |
| 叠加 | **只能选一个**（优惠码 / 店员打折 / 积分 / 回头券，四选一） |
| 到店付款 | **店员点「💵 Collected」确认收到钱之后**才给分 |

### 积分按什么算（这条最容易搞错）

**基数 = 小计 + 外送费 − 折扣额。** 既不含税（那是政府的钱），也不含小费
（那是客人给店里人的心意）。而且用的是**折后**的小计——否则一个客人用 200 分
抵掉 $5，这 $5 又能给他赚回 5 分，等于积分在给自己生积分。

### 「二选一」是服务端强制的

`server.js` 的 `resolveOrderDiscount()` 同时收到优惠码和积分请求时直接
拒绝（`one_discount_only`）。前端把两个入口做成互斥只是让人少点错，
**真正的关在服务端**。

### 到店付款必须先点「💵 Collected」

这是整条链路上**最反直觉的一处**：厨房看板以前只有「Re-check」按钮，
而 Re-check 只对 Stripe 单有意义，所以到店付款的订单在看板上永远是
`UNPAID · collect $X`，谁都点不掉。

于是「店员确认收款后才给分」这条规则**缺一个按钮**。现在有了：
看板每张到店付款的单子上有个 **💵 Collected**，点了才 `paymentStatus: paid`，
服务端这才发分。**不是 bug，是规则。**

### 幂等：同一笔订单不会被发两次分

`order.loyalty.awarded` 这个标记挂在**订单**上，不是挂在客人上。
所以 Stripe 回跳、店员 Re-check、店主手动改状态、同一个人点两次
Collected——都只会发一次。取消订单则按 `.released` 把分退回去，
退一次就锁死。

盖章用的是**计数器**（`stampsIssued < floor(settledOrders / 10)`），
不是「已结算订单数是不是 10 的倍数」——后者在店主手动改过计数之后
会给同一个里程碑发第二次奖。

### 手机号就是账号，而且宁可不认也不猜

`normalizePhone()` 把号码剥成数字、丢掉单个前导 1、**要求正好 10 位**。
不够 10 位、11 位但不是 1 开头、12 位及以上——**全部拒绝，返回 null**。

这不是矫情：如果它「取最后 10 位」，一个输错的 11 位号码就会落到
**另一个真实客人的余额**上，分打进了陌生人的账，而且查不出来。
宁可让客人这一单不长分，也不能让他拿到别人的余额。

### 一次只能挂一张回头券

客人连着来五天，不会攒下五张 $5 券。每张已付款订单都会**换掉**最旧的
未使用回头券（已经用掉的不动，留作凭据）。这样回头券始终是**一张正在
倒计时的钩子**，而不是一个可以囤的资产。

配合上面的盖章里程碑，**理论上限是 11–15% 的返利**。这是定规格时就算过
的：一家外带店的净利大概 10–20%，所以这不是可以顺手再加的筹码。

### 店主能做什么（后台 `⭐ Members & Rewards` 卡）

- 按手机号或姓名搜会员，看余额、券、最近动向
- **导出 CSV**（带 BOM，Excel 直接打开不乱码）
- **手动补录**：加/减分（`delta`）、发一张一次性券（`coupon`）、写备注。
  把余额调到负数是**报错**的，不是悄悄夹到 0。

/api/customer?phone=...  # 公开：查自己的余额、券、盖章进度（限流 60 次/分）

## 五点九、月度会员费 + 限时段 Delivery（⚠️ 2026-10-14 写完、测完，**尚未发布**）

> 和五点八一样：**本地完成，一行都没上线。** 会员和配送都牵到钱，发布前先把规则确认死。

### 月度会员费（店主手动确认，不绑卡）

**没有自动续费、没有存档卡、不和 Stripe 订阅挂钩。** 会员身份就是一个时间戳
`memberUntil`：店主确认收到这个月的会费 → `memberUntil` 往后滚一个周期，顺手发一张
这个月专属的券。客人那边只是一串到期时间，没有可被扣款的凭据 —— 少一个会自己
扣钱的东西。

四项权益（加上「会员折」共**五个互斥项**，见下）：

| 权益 | 默认值 | 配置项 |
|---|---|---|
| 每单固定折扣 | 5% | `member.percent` |
| 免配送费 | 开 | `member.freeDelivery` |
| 积分 ×2 | ×2 | `member.pointsMultiplier` |
| 每月专属券 | $5 | `member.couponValue` |

会费金额、周期都是配置项（默认 **$9.99 / 30 天**）：

```js
member: { enabled: true, fee: 9.99, periodDays: 30, percent: 5,
          freeDelivery: true, pointsMultiplier: 2,
          couponValue: 5, couponDays: 30, couponLabel: 'Member reward' }
```

**配置错误 fail closed，而且「缺失」不等于「写坏了」：** 整块 `member` 没配 → 用默认值；
只有某一个值读不出来 → 那一项按 **0** 算（折扣率不会变成 100%，倍数不会变成 0 反噬）。

**幂等按「续费日」，不按毫秒。** `memberCouponIssuedFor` 存的是 `YYYY-MM-DD`。
店主手抖点两下「确认续费」，滚期只滚一次、券只发一张 —— 而不是两种各发一遍。
（到店收款是人工确认，双击是常态，不能用毫秒去重。）

### 权益也是「一单只给一个」

会员不是叠 buff：**优惠码 / 店员打折 / 积分 / 回头券 / 会员权益，五选一**。
会员折走的是和积分同一条 `applyDiscount(type:'amount')`，报错也分得清
（余额不足 `points_unavailable` ≠ 单太小 `order_too_small`）。

> 积分倍数只在**服务端发分时**注入（`awardForOrder(cust, order, now, { pointsMultiplier })`），
> **绝不从订单 payload 里读** —— 和不信客人自称 `paymentStatus` 是同一条规矩。
> 分数先按整数分算，再乘倍数，再取整：$15.99 基础 15 分，×2 会员得 30 分；
> payload 里伪造的 `50×` 会被忽略。

### 限时段 Delivery：次日起、每时段限量、便宜

- **只从明天起。** 今天不能点配送（`ahead >= 1`），最多可往后选 `maxDaysAhead` 天。
- **每天每个时段有单量上限。** 满了这个时段就**不可选**（灰掉），而不是先下单再拒。
- **运费是配置项，会员可免。**
- **时段必须落在营业时间内**，否则 `slot_outside_hours`。
- **日期用本地 `YYYY-MM-DD` + 天数运算**，不做毫秒运算（DST 安全）。

**容量从实时订单推导**（数同一天同一时段、未取消的单），**不新增第 8 个持久化文件**。

创建订单时的 payload 是 `{ schedule: { date, slot } }`：

| 情况 | 回应 |
|---|---|
| 非配送单带了 `schedule` | `schedule_not_delivery` 400 |
| 配送单没带 `schedule` | `schedule_required` 400 |
| 渠道关着 | `delivery_unavailable` 409 |
| 日期/时段不合法（太远 / 不营业 / 满） | `resolveSchedule` 的 verdict 409 |
| 金额对不上 | `total_mismatch` 400（**先跑**，在 schedule 检查之前） |

### 「已付款」不等于「现在就做」

这是整条链路上最容易做错的一处：**明天的配送单，就算钱已到账，也绝不能现在跳进厨房。**

`shouldAutoPrepare()` 里有一道窗口守卫：

```js
if (scheduledForMsOf(order) > Date.now()) return false;
```

未来的单先停在 `received`，等 `startScheduleLoop()` 的定时器到了窗口（窗口起点 −
`leadMinutes`）才进厨房。打印是由「状态 → preparing」这个跃迁触发的，所以它**自动
跟着延后**，不需要在打印里再写一遍。付款是必要条件，不是充分条件 —— 有测试专门
从两边钉这条（钱确认了、但单不动、也不出票）。

### 静态配置 vs 运行时开关（别再搞混）

订单渠道的**运行时开关**（看板上的 `storeStatus.orderTypes.delivery`）是权威，
它**覆盖**静态的 `config.delivery.enabled` 种子值。以前 `pricing.js` 只读静态配置，
于是「运行时把配送打开 → 运费恒 0」，价格和实收会对不上。

现在统一在一处缝上：`deliveryPricingOpts()` 把运行时的配送状态交给计价器，
`/api/price`、服务端实收、厨房票**用的是同一个判断**。
`/api/schedule` 也是公开接口，`enabled` 取的就是运行时开关。

> ⚠️ **Online Delivery 渠道仍关着**（`config.delivery.enabled:false`，店主 10-13 20:45
> 也把渠道关了）。本节的规则先落好，渠道等店主点头再开。

## 六、订单数据的备份与导出

订单保存在 `orders.local.json`（容器本地文件，**重新发布 / 容器重启就没了**）。
为了不至于真的丢单，服务里加了两层保险：**自动滚动备份** + **后台一键导出**。

### 导出（店主用，需 admin key）

两个只读接口，都在后台鉴权后面，**不改动订单数据**：

| 接口 | 内容 | 用途 |
|---|---|---|
| `GET /api/orders/export.csv` | 一行一单，Excel / 飞书表格直接打开 | 交给会计、对账、算营业额 |
| `GET /api/orders/export.json` | 完整原始数据（含每道菜、桌号、付款状态） | 留档；以后要做「导入恢复」用这份 |

可选时间过滤（按**下单时间**）：

```bash
# 只看 2026-10-04 一整天
curl -H "X-Admin-Key: <adminKey>" \
  "https://<线上地址>/api/orders/export.csv?from=2026-10-04&to=2026-10-04T23:59:59"
```

CSV 的列固定为：

```
id, at, updatedAt, status, paymentStatus, payMethod, orderType, table,
customerName, customerPhone, subtotal, tax, tip, delivery, total, itemsSummary
```

`itemsSummary` 把每道菜压成一行，例如 `2x BBQ To Go (2 Meats) [Pork Belly, Beef Brisket]; 1x Thai Tea`。

下载下来的是附件（`Content-Disposition`），文件名带日期。CSV 带 **UTF-8 BOM**，
Excel for Windows 打开中文 / 特殊字符不会乱码；单元格里所有 `"` 都会转义，
并且**开头的 `=` `+` `-` `@` 会被中和**——客人把名字填成公式也执行不了（CSV 注入防护）。

### 自动备份（无需人工）

服务会把「当前全部订单」快照成 **CSV + JSON 两份**，写进备份目录：

```
order-backups/
  orders-2026-10-04.csv
  orders-2026-10-04.json
```

写盘时机：

| 时机 | 原因 |
|---|---|
| **启动时** | 先把刚加载进来的盘上数据存一份，保证这天一定有备份 |
| **每 24 小时** | 长期运行的兜底 |
| **订单有变化后最多 30 秒** | 见下面的「为什么需要这个」 |
| **正常关闭时**（`SIGTERM` / `SIGINT` / `exit`） | 重新发布前最后存一次 |

每天一个文件，只保留 **30 天**，超期自动清理（`pruneBackups`），不会把磁盘撑满。
写入用**临时文件 + rename** 的原子写法，中途崩了也不会把好备份覆盖成半截文件。

可配置项：

| 变量 | 默认值 | 说明 |
|---|---|---|
| `ORDERS_BACKUP_DIR` | `<项目目录>/order-backups` | 备份目录。**如果平台能把这个目录挂到持久卷上，备份就能跨发布保留** |
| `KPOT_FLUSH_MS` | `30000`（30 秒） | 订单变化后的刷盘间隔；测试用，最小 500ms |

> 这两个环境变量的值**不会**从线上地址猜出来，每个变量直接写在部署配置里即可。

### ⚠️ 一个容易踩的坑：Windows 上关闭钩子根本不跑

实测过（`_dev/probe_sigterm.js`）：**Windows 给 Node 进程发 `SIGTERM` 时，
`process.on('SIGTERM')` 和 `process.on('exit')` 都不会执行**——进程被直接终结。
也就是说，在 Windows 本地跑的时候，指望「关闭时存盘」是**不成立的**。

所以真正兜底的是那个 **30 秒刷盘循环**（`startFlushLoop`）：只要订单有变化，
最多 30 秒一定落盘 + 落备份，进程被硬杀也最多丢这一小段。
`_dev/test_flush_survives_kill.js` 就是为这条路径写的测试——**不发任何信号，
直接 `SIGKILL`，重启后订单仍在**，输出 `PASS — periodic flush saved the order without any shutdown handler`。

线上跑在 **Linux 容器**里，信号处理是正常的，关闭钩子会照常执行；
但**不要**把数据安全建立在关闭钩子上，这条 30 秒兜底对两个平台都有效。

### 备份目录不能从网上读到

`order-backups/` 在静态文件服务里是**目录黑名单**（`BLOCKED_DIRS`），
`/order-backups/` 及其中任何文件一律 404；`orders*.csv` 也被扩展名/路径拦截。
要看备份内容只能走上面那两个带 admin key 的导出接口。

### 关于「挪到托管数据库」

目前的方案（本地文件 + 滚动备份 + 后台导出）适合**单实例**经营：
不丢数据靠备份，随时能把账导出来。**代价**是：
重新发布会**丢掉当天的订单看板**（备份文件还在，要看就重新导），
且**多实例不会共享订单**。

真想长期跑 / 多实例，就应该把订单挪到外部存储（webhook 转发到 Google Sheets /
Airtable，或托管数据库如 Supabase / Firebase）。那是一条独立的改造，
现在没做，需要的时候再说。

## 九、技术说明

- 纯前端部分：无框架、无构建步骤；后端只有 `server.js` + `pricing.js`，**零第三方依赖**
- 购物车存在浏览器 localStorage，刷新不丢
- 金额采用「先分项四舍五入再求和」，保证票据上每一栏相加都等于总计
- 订单号按天自增：`KP-YYMMDD-NNN`
- 打印样式已适配：票据可 80mm 热敏纸直出

### 安全设计（重点）

| 机制 | 说明 |
|---|---|
| **服务端重新计价** | 浏览器只说「点了什么」，**从不参与算钱**。`pricing.js` 用 `vm` 重新加载 `menu.js` 从菜单里逐行算价，改前端价格、伪造 `+999.00` 这类字符串都无效 |
| **密钥不落地** | Stripe secret key 只存在于服务进程里，不下发浏览器、不打日志、不当作静态文件提供 |
| **静态文件白名单** | 只提供已知扩展名；隐藏文件一律 404；`secrets*.json`、`server.js`、`pricing.js`、`package.json`、`make_qr.py`、`README.md`、`url.txt` 全部屏蔽；并用 `path.relative` 兜底防止目录穿越 |
| **限流** | 单 IP 每分钟最多 20 次结账请求 |
| **请求体上限** | 64 KB，超出直接 413 |
| **数量上限** | 单笔最多 60 行、每行最多 50 份；小费比例封顶 50% |
| **超时** | 调用 Stripe 15 秒超时（`AbortController`），避免请求悬挂 |
| **幂等** | 每次结账带 `Idempotency-Key`，网络重试不会重复扣款 |
| **错误不泄露** | Stripe 的原始报错只写服务器日志，客人看到的是可操作的提示 |

### 支付返回流程

Stripe 付款后会带客人回到 `?paid=1`（成功）或 `?canceled=1`（放弃）：

- **成功** → 从 `localStorage` 取回下单前暂存的订单，显示**已确认票据**
  （票据上的金额用的是**服务端算出的数**，与 Stripe 实收金额分毫不差）
- 地址栏参数会立即被清掉，**刷新 / 分享链接不会重放这张票据**
- **放弃** → 提示「订单未提交」，客人回到菜单，购物车还在；
  同时**服务端会把这一单在看板上取消**（见下）
- 客人**无法**靠改地址栏伪造一张已付款的票据——票据只认本地暂存的那份订单，
  而且票据上的付款状态来自服务端**真的问了 Stripe** 的结果

#### 看板由服务端结算，不由浏览器改（重要，别改回去）

订单在**付款之前**就记到看板上了（必须这样，否则订单号占不住）。所以：

| 情况 | 看板上的结果 | 由谁触发 |
|---|---|---|
| 客人付了钱 | `paymentStatus` → `verified` | `/api/verify-session`（客人浏览器回来报信时） |
| 客人放弃付款 | `status` → `cancelled` | 同上 |
| **客人付了钱但没回来报信** | 一直停在未核对 | ⚠️ **没人触发** —— 要靠员工点 **Re-check payment** |

**前两件事都由服务端的 `/api/verify-session` 做**，因为：

1. 客人页面**改不了**看板。`PATCH /api/orders/:id` 是**要 admin key** 的，
   客人没有——浏览器发过去的 PATCH 会**静默 401**。
   这个 bug 一直存在，直到用**真实 Stripe 密钥**跑端到端才暴露出来：
   客人明明付了钱、票据上写着「Pay Online ✓」，**厨房看板上却还是未付款**。
   （旧的桩测试服务器在 PATCH 上没有鉴权，所以一直没露馅。）
2. 服务端做更可靠：证据是 **Stripe 自己的 session 数据**（
   `client_reference_id` 就是我们的订单号），不是浏览器说了算。

> ⚠️ **不要**再把看板更新写回客人页面。那个接口客人调不动，
> 而且**失败是静默的**（401 没有提示）。

#### ⚠️ 别以为「服务端结算」= 覆盖了所有情况（这是踩过的坑）

`/api/verify-session` **只有客人浏览器真的来调它**才会跑。
`sessionId` 只存在**客人浏览器的 `localStorage`** 里，**服务端从来没存过**。
所以「客人付完钱关掉页面」这种情况，**服务端根本不知道有这一单**，
看板会永远停在未核对。

早期 README 在这里写过「客人就算付款后直接关掉页面，看板照样会结算」——
**这句话是错的**，而且正是它让 `KP-261007-001` 那个问题一直没被想到。
别再写回去。

补上这个缺口的就是 **`POST /api/orders/:id/recheck-payment`**（要 admin key）：
服务端**按订单号去 Stripe 找会话**（用 `client_reference_id`），
不依赖浏览器交出来的任何东西。细节见第五节「💳 Re-check payment」。

## 十一、Apple Pay / Google Pay 用不了怎么办

钱包**不是**点餐页上的独立选项。Stripe 把它们塞在**自己的刷卡表单里**，
只有客人设备支持时才出现。所以「按钮没出现」通常是正常的，不是 bug。

### 先分清两种「不行」

| 现象 | 含义 |
|---|---|
| **按钮根本不出现** | 设备不支持，或后台钱包开关没开 |
| **按钮出现，点了报错** | 比如 `CALLBACK_TIMED_OUT` —— 设备/环境问题居多，见下 |

### 排查顺序（按性价比）

**第 0 步：先换设备验证，再动后台。**
用**桌面版 Chrome**，**从地址栏直接打开**点餐页（不要从微信 / Instagram /
TikTok 等 App 内点开 —— 内置浏览器里 Google Pay 基本必然失败）。
如果这样就成功，代码和后台都没问题。

**第 1 步：确认 Live 模式。**
Stripe 后台右上角必须是 **Live**。Test 和 Live 的支付方式是**两套独立设置**。

**第 2 步：打开钱包开关。**
`Settings → Payment methods → Wallets` → 把 **Google Pay** / **Apple Pay** 打开。

```
https://dashboard.stripe.com/settings/payment_methods
```

> ⚠️ 这里是**单独的开关**。`card` 开着**不代表** Google Pay 开着 ——
> `/api/payment-methods` 探针只能证明 `card` 开着，证明不了钱包开关。

**第 3 步（仅 Visa 卡）：** 在 Google Pay & Wallet Console 里开启
**Fraud Liability Protection for Visa Device Tokens**。

**第 4 步（仅 Apple Pay）：** `Settings → Payment method domains` 里
添加并验证域名。Apple 要求域名关联文件，否则开关即使开着按钮也不出现。

### 关于 `CALLBACK_TIMED_OUT`

这是 **Google Pay 的错误，不是 Stripe 的**。意思是 Google Pay 面板弹出来了，
但 Google 无法完成对商家的域名握手。

本项目用的是 **Stripe 托管结账页**（跳转到 `checkout.stripe.com`），
Stripe 官方明确说明：托管界面**自动支持** Apple Pay / Google Pay，
**无需向 Apple 或 Google 注册域名**（域名注册只针对 Elements /
Checkout 嵌入式表单）。

> ❌ **不要**为了修这个问题去买 $10/月的 Checkout 自定义域名 —— 方向反了。

### 一个容易忽略的坑：域名会变

自建支付集成里，钱包是**认域名的**，而本项目的 App 域名**每次发布都会变**。
托管结账页绕开了这一点（Google 看到的是 `checkout.stripe.com`）。
**如果哪天改成自建支付表单，这个问题会立刻回来** —— 到时必须配一个稳定域名。

> ⚠️ **2026-10-22 第三次，教训最钝**：`probe_credit_http` 为了测「一单只能

> `KPOT_MENU_FILE`），并且**五个文件全部纳入指纹比对**。

### 浏览器测试要**真的**删掉自己的临时目录

`probe_cleanup.js` 是给两个浏览器套件共用的收尾工具，起因是一个**静默的泄漏**：

`chrome.kill()` 只杀**你 spawn 的那个进程**，而 Chrome 是一棵树
（browser + gpu + network + renderer）。紧接着 `fs.rmSync(--user-data-dir)`
会和这棵树的退出**抢跑**：句柄还没放，`rmSync` 抛 `EBUSY`，
而调用处包着 `try/catch` —— **失败是静默的**。于是每跑一次就悄悄在
`%TEMP%` 里留下一个 10–95 MB 的目录。实测：一个套件跑两次留下 22 MB + 12 MB，
更早的套件每个留 94 MB，**攒了好几天没人发现**。

修法：**杀整棵树（`taskkill /T /F`）→ 等它真的死 → 带重试地删**；
删不掉就**打印一行**，让泄漏是看得见的而不是静默的。
`run_all.sh` 里的浏览器套件都走这个工具。

> 判据：**「测试全绿」不等于「测试没留下垃圾」**。收尾的每一步都要能被验证，
> 尤其是那些包在 `try/catch` 里的——它们失败的时候最安静。

### ⚠️ `waitFor` 把「抛异常」当成「等到了」（2026-10-22 抓到并修掉）

十个浏览器套件共用同一个 `waitFor(expr, …)`：轮询 `Runtime.evaluate`，
**返回值 truthy 就认为等到了**。它的 `catch` 长这样：

```js
try { last = await evalJs(expr); } catch (e) { last = '(ctx) ' + e.message; }
```

`'(ctx) …'` 是个**非空字符串，永远 truthy**。于是只要表达式**抛异常**，
`waitFor` 立刻返回、宣布成功——而这个条件从来没成立过。

真实症状：`probe_guest_discount` **大约每 15 次里飞 7 次**，单独跑经常全绿、
整套跑才飞。它等的是「折扣行变成 Store credit」，而应用在重新计价期间会把
折扣行**从 DOM 里摘掉**（先清金额再问服务端），中间有约 10ms 的空窗：

```
… 折扣行 "Discount · TEN-$3.20"        ← 优惠码已生效
… 折扣行 (ABSENT)，储值框已清空          ← applyCredit 摘掉折扣行，请求在飞
… *** 检查在这时跑 ***                  ← 读到的行不存在 → FAIL
… 折扣行 "Store credit-$31.98"          ← 10ms 后请求回来了
```

**诊断值在检查当时是非空、紧接着的详情行却是空**——这个矛盾本身就是证据：
说明变的是**页面**，不是断言。用 `MutationObserver` + `addScriptToEvaluateOnNewDocument`
（**不加扰动地**记录折扣行和储值框的每一次变化）才拿到这条时间线。

修了两层：

1. **helper**：抛异常 = 没等到，继续轮询；错误只在真的超时时才报。
2. **表达式**：`(x||{}).textContent` 在元素不存在时是 `undefined`，
   `.indexOf` 直接抛。改成 `((x||{}).textContent||'')`，根本抛不出来。

> 判据：**轮询 helper 的 `catch` 分支是最容易造假绿的地方**——它把「我读不到」
> 翻译成了「我读到了」。凡是 truthy 即成功的等待，都要问一句：失败的返回值
> 长什么样？会不会刚好也是 truthy？

### ⚠️ 跑测试用的 `env` 会「假绿」（2026-10-12 抓到并修掉）

`run_all.sh` 原本用 `env "$@" node <suite>` 跑每个套件。这台机器上
**`C:\Users\shige\.local\bin\env` 排在 `/usr/bin/env` 前面**，而它其实是个
只改 PATH 就退出的 shim（328 字节，**根本不执行后面的命令**）：
吞掉所有输出、**退出码永远是 0**。后果是最恶劣的一种假绿 ——

> 故意删掉 `server.js` 里 `auto-prepare` 的 fail-closed 那行，
> `run_all.sh` 照样打印 `20 passed, 0 failed`。每个套件其实根本没跑。

现在 `run_all.sh` 有两道防护：

1. 启动时**逐个试**候选 `env`，挑一个能真的把 `echo` 的输出吐出来的；找不到就用
   绝对路径的 node 直接跑。
2. **没有任何输出的套件一律判失败**（真套件必然有结论行），并打印 `no output`。

> 判据：改完跑测试工具本身之后，必须**再故意弄坏一次 `server.js`**，
> 确认 `run_all.sh` 这次真的把 `test_auto_prepare` 标成 FAILED。
> 修好了不等于验证过了 —— 这类「工具说自己成功」的失败模式，
> 只有把断言弄红才能看见。

> 为什么定这条规矩：这些开关是**补上来的**。在此之前，
> `probe_counter_cap_http` 每跑一次就往店主的看板上留两张垃圾订单
> （注释里还写着「已备份、跑完会还原」，实际上根本没做），
> `test_flush_survives_kill` 也直接写真实的订单文件。
> 一次「测试全绿」的背后，看板上多了三张假单子——**而且没人会注意到**。

### 写新测试时的四条纪律

1. **故意把它弄红一次。** 断言写反、正则匹配到注释里的值、桩服务器少了鉴权
   ——这几种「假绿」都真实发生过。新测试必须手动破坏一次，确认它真的会失败。
2. **桩测试看不见「鉴权」**。桩服务器把外部边界换掉时，顺手把
   「这个接口客人调不动」也换掉了。所以凡是有鉴权的接口，
   都要用**真服务端**测（见 `test_print_auth`）。
3. **浏览器里别用 `textContent` 的子串去断言徽章。**
   看板卡片的一行是**一串相邻的 `<span>`**，`textContent` 会拼成
   `receivedPAID#…`。`\bPAID\b` 里的 `\b` 要求前面是非单词字符，
   而 `received` 的 `d` 是单词字符——**所以这个正则永远匹配不上**，
   测试会一直红在「看起来完全正确」的代码上。
   正确写法是**断言徽章元素本身**：`!!querySelector('… .o-head .pill.paid')`。
   这不只是绕开坑，它本来就是**更强的断言**——颜色是由 class 决定的。

   > 这个坑是在给 Re-check 写 UI 测试时踩到的：服务端日志明明写着
   > `board settled by Stripe: … (verified)`，页面也确实重绘了，
   > 但断言就是不通过。差点误判成「前端没刷新」。

4. **页面里有「顺手发出去的、没 await 的刷新」，就不要在它之后立刻读结果。**
   看板的 `load()` 会 `loadPrinter()` 但**不 await**（`admin-orders.html`
   第 502 行）。于是「订单徽章已经变成 PRINTED」和「打印机状态行已经更新」
   是**两次独立的请求**，前者先落地。测试如果等到徽章一变就读
   `#printerText`，读到的可能还是上一轮的 `No print agent has ever connected…`
   ——**实测大约每三次跑挂一次**，而且挂了以后看起来像功能坏了。

   ```js
   // 错：等到徽章变了就立刻读，读到的是上一轮的状态行
   await cdp.waitFor('… /PRINTED/.test(…)', 25000, 'PRINTED');
   const line2 = await cdp.evalJs('… #printerText …');

   // 对：等「你要断言的那一行」自己到位
   await cdp.waitFor('/ready/i.test(…)', 20000, 'the printer line to say ready');
   const line2 = await cdp.evalJs('… #printerText …');
   ```

   > 判据是：**测试等待的条件，必须就是它接下来要断言的东西**。
   > 等 A 却断言 B，中间就有一段没人管的窗口。
   > 注意别把等待写成断言的复读机——**同一次等待之后要留一条能独立失败的断言**
   > （这里等的是文字，独立断言的是 `class` 里有没有 `ok`）。
